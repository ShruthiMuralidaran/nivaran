How Nivaran works

What happens on each request, which model runs it and why, what it costs per session and at 10,000 officers, and what we have not built yet.

Resolution Copilot · drafting a reply

Up to 4 AI calls per draft. Blue = AI; dashed = our code.
1 · Retrieve
BM25 search over the SOP knowledge base; scheme given or auto-detected. No SOP → no draft.
2 · Draft
Model writes the reply from the officer's findings and cited SOP sections only.
3 · Verify
Every citation must exist; every deadline or amount must be cited or come from the findings.
4 · Self-check
The Judge scores the draft against the five failure modes.
5 · Revise
If checks fail, the problems go back to the model once; the better-scoring draft is kept.

Resolution Judge · checking a reply

1 AI call per check
Input
Complaint + officer's reply (+ scheme)
Retrieve
Matching scheme SOPs + grievance-handling standard
Score
Model returns 5 criterion scores, failure modes with exact quotes, facts to verify (JSON). Today's date is supplied.
Check
Quotes not found in the reply are dropped. Score = average, then caps; verdict by fixed thresholds.
Output
Score, verdict, evidence, cost

Model

Set in one place (api/_lib/config.js or the LLM_MODEL setting)

Why a proprietary API

  • Reliable JSON output and multilingual input (Hindi tested) at low cost.
  • No GPU to run for a prototype; a pay-per-call cost that scales with use.
  • Swappable: Gemini or OpenAI with one setting; the eval script re-tests any swap.

Trade-offs we accept

  • Citizen text goes to a foreign API. A department that requires data to stay in India would need an India-hosted open model (hybrid).
  • Free-tier keys hit rate limits under load; production needs a billed key. The app retries automatically.

What we'd change at scale

Batch the Judge overnight. Closures don't need an instant score; batch APIs list about 50% off.
Embeddings when the SOP base grows. At 22 sections BM25 is fast, free and explainable; with thousands of official SOPs we would add vector search (Supabase pgvector).
Cheaper model if it passes our tests. Run npm run eval on the candidate; switch only if agreement holds.
Keep answers short. Output tokens cost several times more than input; the JSON format and word limits are our main cost lever.

Honest limits

  • Illustrative SOPs. The knowledge base below was written for this prototype, modelled on how scheme rules are structured. It is not official text.
  • The Judge reads text; it cannot check records. It lists the facts a supervisor should verify instead of calling them true or false.
  • No outcome signals yet. Whether the citizen re-filed or appealed is what would make the Judge hard to game with good-sounding text. That needs CPGRAMS data access.
  • No case-record integration. The officer types the findings; in production they would come from the scheme database.
  • Usage log, not case records. Supabase stores the SOP knowledge base and a numbers-only log of each AI request (tokens, cost, verdict, time). Complaint and reply text are never stored.
